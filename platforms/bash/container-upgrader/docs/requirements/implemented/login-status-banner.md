# Requirement: Login Status Banner

## Scope
[[run-summary-log]] gives `container-upgrader.sh` a persistent record of what
happened on its last run, but a user still has to know to go look for it.
On a headless home-lab host, the natural place to surface that
automatically is the login banner every SSH/terminal session already
shows — e.g. Ubuntu/Debian's dynamic MOTD (`/etc/update-motd.d/`), which is
what produces the "Documentation/Management/Support" and "N updates can be
applied" lines seen on a real login to one of these hosts. This requirement
adds a `--status` mode that renders one line from the run-summary-log, plus
`--register-banner`/`--unregister-banner` to install/remove the
`/etc/update-motd.d/` hook that runs it automatically.

This is Ubuntu/Debian-specific (`pam_motd`'s dynamic MOTD mechanism, via
`/etc/update-motd.d/`) — not a generic cross-distro or cross-platform
facility. It is layered entirely on top of [[run-summary-log]] and adds no
new state of its own beyond the generated MOTD file.

## Requirement

### 1. `--status`
An early-exit flag (same tier as `--upgrade-check`/`--upgrade-only`): parsed,
then dispatched *before* `upgrade_main` (no self-upgrade check) and before
engine auto-detect/the `jq`-for-engine-work check (no docker/podman
dependency at all — this must work even if neither engine is reachable by
whichever user runs it).

Behavior:
1. If `jq` isn't on `PATH`, print nothing, exit 0.
2. Read the last line of `STATE_LOG_FILE` ([[run-summary-log]]). If it
   doesn't exist, is empty, or isn't valid JSON, print nothing, exit 0.
3. `not_ok = containers_not_uptodate + containers_update_failed` from that
   entry.
   - If `not_ok > 0`: print `"$not_ok container(s) are awaiting upgrade."`,
     exit 0.
4. Otherwise, compute days elapsed between that entry's `date` (parsed via
   the existing `parse_to_epoch` helper) and now (UTC).
   - If `days >= $STATUS_STALE_DAYS`: print
     `"Containers were last upgraded $days day(s) ago."`, exit 0.
   - Otherwise: print nothing, exit 0.

`--status` never exits non-zero and never prints anything to stderr on a
missing/unparseable log — this runs unattended on every login, and must
never break one or show noise.

### 2. `--status-stale-days N`
Sets the threshold used in step 4 above. Default: `3`. A separate,
explicit numeric option (not a value taken directly by `--status`) —
consistent with every other numeric option this script already has
(`--timeout N`, `--precheck-seconds N`, `--external-restart-wait N`,
`--recent-restart-threshold N`), all of which are always their own distinct
`--flag N`, never a mode flag that optionally also takes a value.

If given without `--status` or `--register-banner` (a normal run,
`--unregister-banner`, `--upgrade-check`, `--upgrade-only`), it is
rejected with an error and exit 1 — it has no meaning there, so silently
ignoring it would hide a mistake. An explicit-vs-default flag
(`STATUS_STALE_DAYS_EXPLICIT`, same idea as `ENGINE_EXPLICIT`) is what lets
the check distinguish "user passed it" from "still the default 3".

### 3. `--register-banner`
Another early-exit flag, requires root (`$EUID -eq 0`, else a clear error
and exit 1 — never invokes `sudo` itself, same pattern as the existing
`systemd_unit_permission_denied` requires-root case).

1. Target user: `${SUDO_USER:-$(id -un)}` — i.e. the user who invoked `sudo`,
   or the current user if run directly as root with no `sudo`. The
   generated banner always shows *that* user's status, regardless of who
   actually logs in later — there is no dynamic per-login-user detection.
2. Resolves this script's own absolute path (`resolve_script_path`, via
   `cd "$(dirname "$SCRIPT_PATH")" && pwd` — the same "$0 is a real path"
   assumption the self-upgrade subsystem's `SCRIPT_PATH` already relies on
   elsewhere in this script).
3. Writes `${MOTD_DIR}/${MOTD_SCRIPT_NAME}`
   (`/etc/update-motd.d/92-container-upgrader`):
   ```bash
   #!/usr/bin/env bash
   # Auto-generated by container-upgrader.sh --register-banner for "<user>" - do not edit by hand.
   # Re-run --register-banner to regenerate, or --unregister-banner to remove.
   su - <user> -c '<absolute-path> --status' 2>/dev/null
   ```
   (`printf '%q'` used for both the username and the `<path> --status`
   command string, so a username/path containing spaces or shell
   metacharacters can't break the generated script.)
   If `--status-stale-days N` was given alongside `--register-banner`, the
   generated command becomes `<absolute-path> --status --status-stale-days
   N` — `--status` always runs with no flags at login, so without this the
   threshold would silently revert to the default 3.
4. `chmod 755` it. Logs a confirmation line and exits 0. Idempotent —
   re-running overwrites the existing file with fresh content (new path,
   new target user if invoked differently).

Only one user's banner can be registered per host at a time — registering
again (even for a different user) overwrites the single
`92-container-upgrader` file. Multi-user registration is out of scope for
this requirement (see "Rejected alternatives").

### 4. `--unregister-banner`
Another early-exit flag, requires root.

1. If `${MOTD_DIR}/${MOTD_SCRIPT_NAME}` doesn't exist: log "nothing to do",
   exit 0.
2. If it exists but doesn't contain the `MOTD_MARKER` comment (i.e. it
   wasn't generated by `--register-banner`, or was manually replaced):
   refuse to delete it, print an error pointing at the file, exit 1.
3. Otherwise remove it, log a confirmation, exit 0.

### 5. Flag-combination validation
`--status`, `--register-banner`, and `--unregister-banner` are mutually
exclusive with each other and with `--upgrade-check`/`--upgrade-only`
(all one-shot administrative modes) — rejected with a clear error and
exit 1, same pattern as the existing self-upgrade flag-combination checks.
`--status-stale-days` is valid only alongside `--status` or
`--register-banner` (section 2).

## Rejected alternatives
- **Detecting the logging-in user dynamically** (e.g. via `$PAM_USER`,
  which `pam_motd` is documented to set for the script it executes) instead
  of baking in a fixed target user at registration time: rejected — this
  can't be verified from a sandboxed dev environment (no live PAM/SSH
  session to test against), and the fixed-target-user design is simpler,
  works identically for both `su`/`sudo`-based invocation, and matches how
  these hosts are actually used (one admin user per host, per the example
  system this was built from).
- **Multi-user banner registration** (each user gets their own MOTD
  fragment): rejected as out of scope for now — `register_banner_main`
  always writes to the single fixed `MOTD_SCRIPT_NAME` path, so registering
  for a second user silently replaces the first. Worth revisiting if this
  is ever needed against a genuinely multi-admin host.
- **A general-purpose `--no-upgrade` flag** distinct from `--status`:
  considered and dropped — functionally identical to the existing
  `--dry-run`, so `--status` alone (implying no self-upgrade check, no
  container-engine work at all, not even a dry-run-style check) covers the
  actual need without a redundant option.

## Rationale
Reusing `--status` inside `container-upgrader.sh` itself (rather than a
separate log-reading tool) keeps the run-summary-log's field semantics and
path resolution defined in exactly one place — the MOTD script becomes a
one-line wrapper with no logic of its own to drift out of sync. Baking the
target user into the generated file at registration time, rather than
detecting it dynamically per login, trades generality (one banner, one
user, per host) for something that's actually verifiable without a live
PAM session to test against.
